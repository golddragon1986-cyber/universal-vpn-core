# ac³: HTTP/HTTPS и переход Vision на чтение

## Главный результат

Ускорение Vision реально наблюдалось, но не оказалось воспроизводимым во всех HTTPS-сеансах. В одном свежем HTTPS/TLS 1.3 запуске sampled CPU-time Mihomo составил 0,60 секунды за 8 секунд, а AES-GCM не попал в выборку. В повторной паре HTTPS/TLS 1.3 потребовал 7,80 секунды CPU и продолжал расшифровывать внешний AES-GCM.

Для медленного повторного HTTPS-сеанса диагностический журнал показал:

```
03:45:21.805 XTLS Vision found TLS 1.3 ... TLS_AES_256_GCM_SHA384
03:45:21.826 XTLS Vision direct write start
```

При этом за весь изолированный прогон: direct_read_count=0, direct_write_count=1, padding_command_2=0. Продолжалась обработка padding command=0 (3551 события; счётчик включает оба теста пары), command=1 встретилась один раз. Отдельных остальных соединений к целевому порту 8080 не было; в обеих частях наблюдалось одно TCP-соединение с отдельным id.

Это локализует симптом: клиент видит TLS 1.3 и переключает направление отправки, но в медленном входящем потоке не получает команду direct read. Это не доказывает конкретный дефект сервера: для отделения серверной логики от особенностей рукопожатия/пакетизации нужны серверные журналы либо трассировка обеих сторон. Один признак HTTPS или TLS 1.3 сам по себе не гарантирует экономный приём.

## Методика

- Один IP RETN Stockholm: 139.45.201.129, порт 8080.
- Один hostname: server-32926.prod.hosts.ooklaserver.net.
- Один ресурс /speedtest/random4000x4000.jpg, заявленный Content-Length 31 625 365 байт. HTTP и HTTPS, HTTP/1.1.
- curl --proxytunnel и --connect-to фиксировали одинаковые адрес и способ доступа через HTTP CONNECT. Использовалось повторное чтение ресурса с keep-alive; в профилируемом окне API подтверждал одно активное TCP-соединение и цепочку SV-inbound.
- Начало CPU-профиля после получения первого МиБ, профиль pprof 8 секунд. Скачанные данные отправлялись в NUL; полного файла ждать не требовалось.
- По подтверждению пользователя видео и прочие загрузки приостановлены.
- Отдельный минимальный Mihomo из уже установленного бинарника, та же canonical connection; только в диагностической копии зафиксирован fingerprint chrome. Рабочие ключи/профили не перезаписывались.
- Защищённый SSH local forwarding с PC loopback 19093/19094 к диагностическим 18881/18882. Доступ к ним в контейнере ограничен source=172.31.41.1 и loopback отдельной временной INPUT-цепочкой.
- Туннель сам расходует CPU роутера и ограничивает скорость. Поэтому суммарный CPU RouterOS и throughput этих диагностических запусков не являются чистым пределом VPN. CPU-профиль относится только к отдельному Mihomo, не к SSH.

## CPU и передача данных

| Запуск | Payload в измерительном окне | Интервальная скорость через SSH | CPU Mihomo за ~8 с | AES-GCM Open cumulative |
|---|---:|---:|---:|---:|
| Первая пара: HTTP | 19 197 712 байт | 17,53 Мбит/с | 6,02 с | 82,56% |
| Первая пара: HTTPS auto | 13 158 750 байт | 12,07 Мбит/с | 7,50 с | 48,27% |
| Свежий отдельный HTTPS, TLS 1.3 forced | 27 851 052 байт | 26,65 Мбит/с | 0,60 с | не попал в выборку |
| Повторная пара: HTTP | 20 264 256 байт | 18,70 Мбит/с | 6,81 с | 78,12% |
| Повторная пара: HTTPS, TLS 1.3 forced | 13 201 952 байт | 12,22 Мбит/с | 7,80 с | 49,49% |

Payload-окно чуть длиннее самого профиля из-за последовательного снятия завершающих счётчиков, поэтому точные CPU-секунды на МиБ по этим окнам не заявляются. Профильные проценты cumulative нельзя суммировать со вложенными функциями.

Тестовый сервер поддерживает TLS 1.2 и TLS 1.3: отдельная проверка Node TLS закреплённого IP получила TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256 и TLS_AES_256_GCM_SHA384 соответственно. Последующая проверка curl без forced TLS также была распознана рабочим Mihomo как TLS 1.3. Поэтому приписывать первую медленную HTTPS-попытку именно TLS 1.2 нельзя — её TLS-версия не была записана.

## Дополнительная проверка рабочего пути

Через обычный прокси 11080 без диагностического SSH-туннеля, исходный рабочий fingerprint randomized:

- HTTP: 17,75 Мбит/с, CPU-снимки 86/44/48/45/39/41%.
- HTTPS с forced TLS 1.3: 13,22 Мбит/с, CPU-снимки 40/60/54/63/58/55%.

В этом RETN-прогоне 100+ Мбит/с из Googlevideo не воспроизведены. Короткая последующая диагностическая HTTPS HEAD-проверка основного процесса зафиксировала как direct write, так и direct read. Это подтверждает, что основной Mihomo способен работать в таком режиме, но не доказывает, что режим был включён в предыдущем медленном GET либо в конкретном видео. Настройки постоянно не изменялись.

## Затруднения и безопасность

Попытка включить pprof сменой API binding без перезапуска не включила debug маршруты. Временное профилирование основного ядра воспроизвело известный сбой randomized/unsupported curve; оно не используется как контрольный результат. Для дальнейшего сравнения применён отдельный минимальный процесс.

Автоматическая проверка отклонила NAT-публикацию неаутентифицированных diagnostic proxy/API для 192.168.0.0/16; эта команда не исполнялась. Пользователь затем явно разрешил временный local SSH forwarding. Все успешные изолированные замеры проводились через аутентифицированный SSH и PC loopback, без NAT-публикации в LAN.

## Восстановление

- Диагностические процессы остановлены, временная INPUT-цепочка удалена.
- SSH forwarding-enabled=no.
- Временных NAT diagnostic правил: 0.
- Основные правила/профиль восстановлены; SV-inbound остаётся Mihomo/randomized.
- log-level warning, pprof 404, панель 200.
- Swap выключен; OOM/high/max=0.
- Финальные SV healthchecks: 469/500/492/501/486 мс. В первой серии Telegram был один HTTPError среди 200; уточняющая серия дала 200/200/200.
