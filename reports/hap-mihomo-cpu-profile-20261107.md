# ac³: CPU-профили Mihomo, 7 ноября 2026

Сняты два CPU-профиля через встроенный Go pprof: 8 секунд при одном и 16 параллельных клиентах HTTP-прокси 192.168.99.1:11080. Тестовый ресурс speedtest.selectel.ru/100MB, временное правило → CHANNEL-SV-inbound. В обоих успешных профилях использовался исходный randomized fingerprint и штатный native Mihomo. Выбор движка проверен до и после. Swap выключен, OOM/high/max=0.

## Результаты

| Параметр | 1 клиент | 16 клиентов |
|---|---:|---:|
| Длительность CPU-профиля | 8,004 с | 8,054 с |
| Суммарное sampled CPU time Mihomo | 4,22 с | 13,54 с |
| CPU samples | 308 | 667 |
| Пик общей CPU по коротким RouterOS-снимкам | 64% | 90% |
| Syscall6, собственная доля CPU | 23,22% | 39,22% |
| ChaCha20-Poly1305 Open, включая вложенные функции | 13,74% | 37,74% |
| gcBgMarkWorker, включая вложенные функции | 1,90% | не попал в выборку |
| gcAssistAlloc, включая вложенные функции | 0,24% | 0,22% |

При 16 клиентах внутренний poll.FD.Write включает 35,82% CPU. Это вложенная доля, её нельзя складывать с Syscall6. ChaCha20/Poly1305 выполняются через функции Generic (quarterRound, updateGeneric, xorKeyStreamBlocksGeneric). runtime.memmove — 2,51% собственного CPU. Правила не относятся к крупным потребителям в этих выборках. Это делает профилирование транспорта/криптографии более перспективным, чем настройку GC или дальнейшую упаковку MRS для увеличения скорости длинного соединения.

Системные вызовы — sampled CPU в соответствующих стеках, а не измерение ожидания USB/сети. Профиль одного клиента заметно включает TLS handshakes (utls.HandshakeContext 16,82%); на 16 клиентах — 0,74%. Профили относятся ко всему процессу: обычный трафик локальных устройств не отключался. По ним нельзя точно приписать каждую долю одному тестовому соединению.

Внутри группы из 16 запросов API подтвердил до 15 одновременно видимых соединений с данными по нужной цепочке. Задано 16 curl-клиентов, но это не гарантия 16 непрерывно передающих сокетов в каждую миллисекунду.

## Существенные ограничения и следующий эксперимент

HTTP Selectel проходит внутри VPN без внутреннего HTTPS. Это важно для VLESS Vision: такой профиль не эквивалентен обычной HTTPS-передаче и не объясняет полностью результат Speedtest RETN. Следующий полезный эксперимент — CPU-профиль длинной HTTPS/TLS-передачи и сравнение доли ChaCha20-Poly1305 с HTTP. Выигрыш заранее не обещается. Менять TLS cipher, сборку или транспорт без этого сравнения преждевременно.

Значения throughput из этого запуска не используются: процессы curl ограничены 25 секундами, их буферизованный write-out не успел сброситься, поэтому учёт объёма неполон. В results.json mbps=null, дано пояснение. CPU-профили сохранены, имеют корректные symbol/function tables и доли flat суммарно 100%.

## Диагностические затруднения

pprof доступен только при старте ядра с log-level debug (согласно исходникам MetaCubeX/mihomo hub/route/server.go и официальной документации API). Поэтому временно сохранены baseline.yaml и диагностическая конфигурация, ядро перезапускалось через свой supervisor. Снятие профилей шло по существующему API 19090, без длительной /container shell.

Первоначальные попытки невалидны и не включены в результаты: неустойчивый randomized uTLS с ошибкой CurvePreferences/восстановлением supervisor; экспериментальная диагностическая копия с firefox не обеспечила устойчивую передачу; Speedtest-go оборвался на получении пользовательской информации. Последние успешные профили получены с оригинальным randomized, экспериментальная копия провайдера не используется. Условия CPU debug-режима и фонового трафика отличаются от чистого бенчмарка.

## Восстановление

После теста восстановлен исходный default_config.yaml из baseline, ядро возвращено в обычный режим. pprof возвращает 404, панель 200, SV-inbound остаётся Mihomo, исходный fingerprint randomized, swap не включался, память без OOM. Изменения профилей, правил и параметров Go постоянно не применялись.
