# VPN: удалённый сервер и задержка после прогрева

В рендере таблицы SOCKS/HTTP loopback-мост sing-box сопоставляется с
конкретным inbound и его однозначным outbound route. Для отображения
берутся только server, server_port и type удалённого outbound. UUID,
ключи и остальные приватные параметры в HTML не попадают.
Провайдер и локальные порты 18181/18182 для транспорта не меняются.

Постоянно включён `unified-delay: true` в шаблоне и рабочих конфигурациях.
В исходнике установленной Mihomo v1.19.33 (adapter/adapter.go, URLTest)
этот режим делает второй HEAD-запрос тем же http.Client и соединением,
отсчитывая задержку второго запроса. Это HTTP-задержка через VPN до
www.gstatic.com, а не ICMP ping до адреса VPN-сервера.

Ограничение upstream: если второй запрос завершится ошибкой, URLTest
может вернуть время первого запроса. Нормальные успешные проверки
возвращают время после прогрева; строгую гарантию отсутствия fallback
эта версия ядра не предоставляет.

Применено в работающем universal-vpn-core. Проверено:
- В /configs unified-delay=true.
- /api/proxy-delay: SB-SV 64 ms, SB-FL 86 ms в контрольной паре.
- В HTML больше нет 127.0.0.1:18181/18182; показаны удалённые адреса :443,
  тип vless · sing-box.
- Связь мостов и реальные endpoints проверены внутри контейнера;
  Python source успешно разобран ast.parse.
